# Artifacts

Design for phase 6: pages a model writes about a change.

An **artifact** here is a self-contained webpage generated by Claude or Codex explaining a
commit or a branch — why it matters, what to look at, with diagrams — in the manner of the
rendered page linked from [`session-bands.md`](session-bands.md), but produced per change
rather than by hand.

Phase 5 built something else. [`export.md`](export.md) carries the correction; the short
version is that "artifact" was read as "the graph, as a file", so the unit came out as the
whole graph and the format came out as SVG. Both were wrong. Nothing below assumes them.

Measurements are against the 39 repositories on this machine and the harnesses installed on
it (`claude` 2.1.220, `codex` 0.144.4).

---

## The brief is the product

The page is authored by the model. This project's contribution is the **brief** — and that
is a better fit for what already exists here than drawing ever was.

| Input | Status | What it gives the page |
|---|---|---|
| Structured diff | `/api/commit` returns parsed `DiffFile`/`DiffHunk`/`DiffLine` | The *what*, already parsed |
| Session title, prompt count, cost | `SessionBandInfo`, phase 4 | The ***why*** — intent behind the change |
| Push markers | `reflog.ts`, phase 3 | When it left the machine |
| Ahead/behind, worktrees | `status.ts` | Where it sits now |
| Lane topology | `lanes.ts` / `rail-paths.ts` | What it branched from and merged into |

The session data is the part worth dwelling on. It was built in phase 4 as a *display*
feature — a label above a band. As a brief it is the only input that carries intent:
`git show` can say five files changed together and cannot say what someone was trying to do.
That is exactly the gap a generated explanation has to fill, and this project already reads
it.

### What is missing

**The prompt text.** `SessionBandInfo` carries `promptCount` but not what was asked.
`claude-code.ts` already parses the transcripts those counts come from, so the text is one
field away — and it is the single highest-value input the brief does not currently have.
It is also the most sensitive: prompts contain whatever was pasted into them. Off unless
explicitly enabled, and never sent for a session the user has not opted in.

## The tail will break this, and binary filtering does not fix it

The obvious plan is to put the diff in the prompt. Measured across the 196 non-merge commits
of the largest repository here:

| | diff size | ≈ tokens |
|---|---|---|
| median | 949 B | 237 |
| p90 | 8,058 B | 2,014 |
| **p99** | **10,524,982 B** | **2,631,245** |
| **max** | **85,199,129 B** | **21,299,782** |

The median commit is nothing — 237 tokens. Every commit in *this* repository sits between
1.8k and 21k tokens, which is why the problem is invisible from inside it. The tail is four
orders of magnitude out, and any design validated only on its own repository ships broken.

The two worst commits fail differently, and that is the point:

| Commit | Size | Binary files | Why it is big |
|---|---|---|---|
| `Update (#67)` | 85 MB | 94 of 157 | ZIP archives and STL meshes |
| `Upload STEP for SO-Arm100` | 10.5 MB | **0 of 1** | One **text** file, 135,037 lines |

Dropping binaries is the obvious mitigation and it is **not sufficient**. The second commit
contains no binary files at all: a STEP CAD file is plain text, git diffs every line of it
happily, and it alone is 2.6 million tokens.

### Budget policy

Three rules, in order:

1. **Binary files contribute their name and nothing else.** `--numstat` reports `-`/`-` for
   them, so they are identified before any content is read.
2. **Per-file diff bodies are capped by line count.** Beyond the cap a file keeps its stat
   line and hunk headers and loses its body. This is what catches the STEP file, which rule
   1 does not.
3. **The bundle has a total budget**, and files are admitted longest-last so a hundred small
   files are not starved by one large one.

The invariant that makes degradation honest:

> **The file list is never truncated. Only diff bodies are.**

So a page can always state completely and correctly *which* files changed and by how much,
and the only thing lost under pressure is line-level detail. A page that silently omitted
files would be worse than one that says "12 files exceeded the diff budget and are listed
without their contents" — and the artifact must say so, on its face, the same way an export
names its scope.

## Harness

Both CLIs are installed and already authenticated. The daemon shells out to one:

```
claude -p --output-format json --model <m> --append-system-prompt <page spec>
```

**A subprocess rather than the API.** The daemon then holds no credentials, stores no API
key, and opens no sockets of its own — the tool the user already runs makes the call. It
also means whichever harness they have configured, including Codex, is the one used, rather
than this project having an opinion about their account.

`--allowedTools` is set to nothing. The model is being asked to write a page from a brief
that is already in its prompt; it has no reason to read the filesystem, and a generator that
can run tools in the user's repository is a different and much larger security question than
one that cannot.

### What the model is told

Two parts, kept separate:

- **The brief** — the bundle above, as structured data.
- **The page spec** — a system prompt fixing the output contract: one self-contained HTML
  document, no external requests, mermaid for diagrams in `<pre class="mermaid">`, and the
  honesty constraints below.

The page spec is a fixed asset in this repository, not something assembled per request. It
is the part that determines whether artifacts look like a coherent series or like fifty
unrelated pages, and it should be reviewable as a file.

### Honesty constraints, inherited

These are not new. They already hold everywhere else here and must survive into a generated
page, which means they belong in the page spec where the model will read them:

- The repository **name**, never its path.
- Sessions are **observed alongside** a commit, never the author of it. A generated page is
  far more likely to assert authorship than a label is, because prose invites it.
- An artifact covering part of something **says which part**, exactly as a scoped export
  names its scope.
- Anything dropped for budget is **stated**, not silently omitted.

## Destination

Generated pages are written to a cache directory outside the repository —
`~/.cache/git-artifact/<repo>/<sha>.html` — and served back for viewing.

This is a new thing this project writes, and the README currently says the only thing it
writes is its own build output. Outside the repository and outside any other tool's
configuration, but it needs saying rather than assuming.

Caching is not an optimisation. Generation costs real tokens, so a page is generated once
per commit and reused; a sha is immutable, which makes it a perfect cache key. Branch pages
key on the tip sha plus the merge base.

Publishing to a shareable URL is deliberately **not** in this phase. A local file is
reviewable before it goes anywhere, and "generate" and "publish" being one button is how
something ends up on the internet that should not have.

## Promises that move

Both are stated flatly in the README today, and both should move deliberately.

| Promise | Now | Becomes |
|---|---|---|
| "No outbound network requests of any kind" | absolute | No telemetry, ever. Generation invokes your local CLI — per click, never in the background. |
| "Anything other than `GET` is refused outright" | absolute | No endpoint mutates **the repository**. Generation is `POST /api/artifact`. |

The second is unavoidable: generation spends tokens and produces a file, a browser cannot
shell out, so the daemon must. The rule that was actually load-bearing — that this tool
cannot damage your repository — is untouched.

## Unit: commit first, then branch

**Commit** ships first. Bounded input, richest context, and it exercises the whole pipeline
— bundle, budget, harness, cache, render — on the unit where every part is simplest.

**Branch** is the same pipeline over a commit range, and it needs one thing commit scope
does not: something to measure against.

### Resolving the merge base

Left open in `export.md`. Measured on five repositories here:

| Rung | Resolved |
|---|---|
| `git symbolic-ref refs/remotes/origin/HEAD` | 3 of 5 — every repository with a remote |
| `init.defaultBranch` | **0 of 5** — set nowhere on this machine |
| first existing of `main`, `master`, `trunk` | 5 of 5 |
| explicit override | always |

The chain covers every repository here: the remote's own default where there is a remote,
falling through to an existence check where there is not. `init.defaultBranch` never fires
and is kept only because it is cheap and correct when set.

A branch page states what it was measured against, because "what this branch adds" is
meaningless without it — and when the base was guessed by the third rung rather than read
from the remote, it says that too.

## Open questions

1. **Which model, and does the user choose?** A commit page is a small job; a branch page
   over forty commits is not. Defaulting to one model and letting `--model` override is
   probably right, but the cost difference has not been measured.
2. **Does a page regenerate when its inputs change?** A commit is immutable, but its
   *session* attribution is not — a transcript written later can change which band a commit
   belongs to. Cheapest correct answer is to key the cache on the bundle, not the sha alone.
3. **Prompt text, on or off by default.** Off is the safe answer and it makes the "why"
   materially weaker, which is the whole point of the feature.
4. **What happens on a bad generation?** The model can return prose that is confidently
   wrong about a diff. There is no oracle here the way `git log --graph` was an oracle for
   lane assignment, and that asymmetry deserves stating rather than glossing.
